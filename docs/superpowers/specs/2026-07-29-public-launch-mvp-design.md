# 可转债持有人网站公开发布 MVP 设计

日期：2026-07-29
状态：方向已确认，等待书面设计复核

## 1. 背景

项目目前是 Flask、Jinja2 和 SQLite 构成的轻量查询站，已经具备以下核心能力：

- 按转债代码、名称、正股名称和拼音首字母搜索；
- 展示转债基础信息、最新一期十大持有人和持有人性质；
- 聚合自然人持仓并估算持仓市值；
- 展示历史下修记录；
- 通过管理后台新增、更新、批量更新和删除转债；
- 提供基础 SEO 页面、robots.txt 和 sitemap.xml。

当前数据库有 1,042 只转债基础资料，但只有 24 只转债采集了持有人数据。应用仍以开发模式为默认运行方式，管理员密码和默认密钥写在配置文件中，公开接口还能触发同步爬取。直接暴露到公网会带来超时、滥用、数据不完整和安全风险。

本次目标是把它整理成一个可免费公开访问、部署在海外、能够尽快验证真实需求的稳健 MVP。

## 2. 目标与非目标

### 2.1 目标

1. 在不重写现有技术栈的前提下达到可公开发布的基本安全标准。
2. 用户访问始终优先读取缓存，外部数据源变慢或失败时仍能使用旧数据。
3. 将耗时爬取从公开 HTTP 请求中拆出，避免页面请求长时间阻塞。
4. 让用户明确知道数据来源、报告期、更新时间、估算口径和可能误差。
5. 提供最小可用的运行监控、错误记录和数据库备份能力。
6. 收集不包含 IP、设备标识或账户信息的最小化搜索统计，用来验证需求。

### 2.2 非目标

首版不实现以下功能：

- 用户注册、登录、会员和支付；
- 自选列表云同步、邮件或微信提醒；
- 实时行情、K 线、回测或投资建议；
- 社区、评论、私信；
- 对外商业 API 和大规模数据导出；
- 为扩展性而迁移到微服务、Redis、PostgreSQL 或前端框架。

## 3. 方案比较与决策

### 3.1 方案 A：直接发布现有应用

只修改管理员密码、关闭 debug 并配置 HTTPS。改动最少，但公开查询仍可能同步调用多个外部数据源，容易被恶意刷新拖垮；空数据页面和失败状态也不够透明。

### 3.2 方案 B：稳健 MVP（采用）

保留 Flask、Jinja2 和 SQLite，增加 SQLite 任务队列、独立采集 worker、生产安全配置、最小监控和可信说明。应用仍然简单，但把公网最主要的安全和稳定性风险隔离开。

### 3.3 方案 C：完整投研平台

同时增加账户、自选、提醒、对比、导出和付费能力。长期扩展空间大，但会延迟上线，也无法在没有真实用户数据时判断功能是否值得开发。

决策：采用方案 B。先验证搜索量、热门转债、无结果查询和详情页访问，再根据数据决定第二阶段功能。

## 4. 总体架构

公开发布后的组件边界如下：

1. **反向代理/TLS 层**：终止 HTTPS，限制请求体大小，对登录和公开 API 做基础频率限制。
2. **Flask Web 进程**：处理页面渲染、缓存读取、管理员操作和任务入队，不执行长时间爬取。
3. **SQLite 数据库**：保存转债、持有人、下修记录、最近浏览、后台任务和最小化搜索事件。
4. **采集 worker**：独立进程读取任务队列，串行或低并发访问外部数据源，完成后原子写库。
5. **定时任务**：通过部署平台定时任务或 cron 调用已有播种/刷新命令，不在 Flask 进程内启动常驻调度线程。
6. **外部数据源**：东方财富、腾讯行情、同花顺和集思录；任何一个失败都不能让 Web 进程不可用。

生产环境建议运行单个 Gunicorn worker 配合线程处理低流量 Web 请求，另启动一个采集 worker。首版继续使用 SQLite，待真实并发或写入量证明需要时再迁移数据库。

## 5. 数据与任务设计

### 5.1 `crawl_jobs` 表

新增后台任务表，主要字段为：

- `id`：任务编号；
- `job_type`：`holders`、`down_revise`、`bond_basic` 或 `price`；
- `bond_code`：单只转债代码，可空；
- `status`：`queued`、`running`、`succeeded`、`failed`；
- `attempts`：已尝试次数；
- `last_error`：截断后的错误摘要，不保存响应正文；
- `created_at`、`started_at`、`finished_at`；
- `requested_by`：`public`、`admin` 或 `scheduler`。

同一转债、同一任务类型只允许存在一个排队中或执行中的任务，避免用户重复搜索造成任务风暴。worker 最多重试三次，并使用退避间隔。

### 5.2 原子更新

持有人数据更新改成单个数据库事务：新数据完整获取并校验后，再替换旧记录和更新时间。任何抓取或解析失败都保留旧数据，不把“抓取失败”写成“没有持有人”。下修记录和基础信息采用同样原则。

### 5.3 更新策略

- 转债基础资料：每天更新一次；
- 价格：首版定位为延迟行情，每个交易日收盘后更新，并展示更新时间；
- 持有人：每周检查一次，管理员可手动入队刷新；
- 下修记录：每天增量检查一次，不能因已有 `down_revise_count` 就永久跳过；
- 首次被查询但尚无持有人数据：立即入队，页面显示“正在采集”，完成后用户刷新即可查看。

上线不以抓完 1,042 只转债的全部持有人为前置条件。已有数据继续保留，其他转债按访问需求采集；没有有效持有人或下修内容的页面暂不进入 sitemap。

## 6. Web 行为与页面设计

### 6.1 搜索和转债详情

- 命中完整缓存：立即返回现有数据。
- 基础资料存在但未采集持有人：创建幂等后台任务，接口返回 HTTP 202 和任务状态，前端显示采集中而不是长时间转圈。
- 外部采集失败且存在旧缓存：继续展示旧缓存，同时标记更新时间和“更新失败，暂用历史数据”。
- 代码、名称或拼音无法解析：返回明确的无结果提示，并记录匿名搜索事件。
- 普通访客不能通过 `refresh=1` 强制实时爬取；更新按钮仅管理员可用，公开页只允许创建受限的首次采集任务。

### 6.2 管理后台

后台保留现有列表、筛选、单只更新和批量更新能力，但所有更新操作改为入队。新增任务状态列表，显示排队、执行、成功和失败数量，并允许对失败任务重新入队。

删除转债仍需二次确认。删除操作只处理明确代码，并在一个事务内删除相关持有人、最近浏览和任务记录。

### 6.3 可信信息页面

新增以下公开页面并在全站页脚提供入口：

- `/about`：网站用途、数据更新机制和联系方式；
- `/disclaimer`：非投资建议、行情延迟、估算误差和外部数据源可用性说明；
- `/privacy`：不提供用户账户、不保存 IP/设备标识，说明最小化搜索统计及保留周期；
- 数据纠错入口：使用配置中的公开联系邮箱，允许自然人或其他主体反馈名称分类和公开数据错误。

自然人页面继续注明信息来自公开定期报告；持仓市值明确标记为基于最新报告期和延迟价格的估算，不表达投资评价。

## 7. 安全设计

1. `ADMIN_USER`、管理员密码哈希、`SECRET_KEY` 和联系邮箱从环境变量读取；生产模式缺少安全配置时拒绝启动。
2. 管理员密码使用 Werkzeug 密码哈希校验，不在源码或日志中保存明文。
3. 会话 Cookie 设置 `HttpOnly`、`SameSite=Lax`，生产 HTTPS 下设置 `Secure`，并设置合理的会话过期时间。
4. 所有管理员 POST 请求使用 CSRF Token；登录和公开任务创建接口增加应用级频率限制。
5. 生产默认关闭 debug，使用 WSGI 服务启动；只信任明确配置的反向代理层数。
6. 添加基础安全响应头：`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options` 和与现有内联脚本兼容的最小 CSP。
7. 用户输入继续通过参数化 SQL 和模板自动转义处理；后台 JavaScript 拼接 HTML 的数据必须先进行转义。
8. 错误响应不返回异常堆栈、外部响应正文、密钥或文件路径。

## 8. SEO 与数据质量

- sitemap 只收录首页、自然人榜单、有有效内容的自然人页、已采集持有人的转债页，以及有下修记录的专题页；
- robots.txt 中使用完整的 sitemap URL；
- 未采集内容和失败状态页面增加 `noindex,follow`，完成采集后恢复索引；
- canonical 使用部署配置中的公开站点地址，避免受伪造 Host 请求影响；
- 保留现有 Breadcrumb 和 FAQ 结构化数据，但结构化内容必须与页面可见内容一致；
- 每个数据模块分别显示数据来源、报告期和更新时间，不能只显示整个页面的统一时间。

## 9. 可观测性、统计与备份

### 9.1 健康检查与日志

- `/healthz` 只检查 Web 进程和 SQLite 的只读查询，不访问任何第三方网站；
- 应用日志输出到 stdout，记录请求错误、任务编号、转债代码、耗时和结果，不记录 Cookie、密码或完整外部响应；
- 统一处理 404、429 和 500，提供中文错误页面和 JSON API 错误格式。

### 9.2 最小化需求统计

新增 `search_events` 表，只记录：截断并规范化后的查询词、解析出的转债代码、命中/未命中结果和时间。不记录 IP、User-Agent、Cookie 标识或跨页面用户身份。统计保留 90 天，并提供后台汇总：热门转债、无结果查询和每日搜索量。

### 9.3 备份

提供使用 SQLite Online Backup API 的备份命令，生成带日期的数据库副本；部署环境每天执行一次，并在保留最近七个日备份后清理更早副本。恢复流程写入部署文档，发布前至少实际执行一次备份和恢复冒烟测试。

## 10. 错误处理

- 所有第三方请求设置连接和读取超时；
- 网络失败、限流和解析失败进入任务重试，不阻塞用户请求；
- 连续失败达到阈值后任务标记失败，后台显示简短原因；
- 已有缓存时永远优先保留缓存；
- 数据校验至少检查转债代码、报告期、持有人名称和数量范围；
- 数据库锁定返回可重试错误，worker 使用短退避；Web 端不向用户暴露 SQLite 异常。

## 11. 测试与验收

新增自动化测试并使用独立临时数据库，至少覆盖：

1. 代码、名称和拼音搜索解析；
2. 持有人性质分类和市值去重计算；
3. 未采集转债只创建一个后台任务并返回 202；
4. 缓存命中不访问网络；
5. 公开访客不能强制刷新，未登录用户不能调用管理员接口；
6. 管理员登录限流、CSRF 和 Cookie 配置；
7. worker 成功、重试、失败以及原子替换数据；
8. sitemap 不包含空内容页面；
9. 404、429、500、健康检查和三张可信信息页面；
10. 备份文件可以打开并读取关键表。

发布验收标准：

- 仓库和页面中不存在可用的默认生产密码或密钥；
- 生产启动不使用 Flask debug server；
- 连续重复搜索同一未采集转债只产生一个任务；
- 外部数据源断网时，首页、已有详情页、牛散榜和后台缓存浏览仍可使用；
- 一次采集失败不会删除已有持有人或下修数据；
- 管理员写操作均有身份校验和 CSRF 防护；
- HTTPS、健康检查、日志、每日备份和恢复测试均已验证；
- 隐私、免责声明、来源、更新时间和纠错入口可从所有公开页面到达。

## 12. 后续阶段候选

首版上线后根据 2 至 4 周真实使用数据决定下一步，候选顺序为：

1. 无账户的本地自选列表；
2. 多只转债横向对比；
3. 持有人跨报告期增减趋势；
4. 下修或持有人变化提醒；
5. CSV 导出和高级筛选；
6. 确认付费价值后再设计账户、会员和支付。

这些候选不属于本次公开发布 MVP 的实现范围。
